# KI-009 — Understanding emits off-enum `capability` and unreliable `goal`/`entities` for tool requests

**Status:** Open (mitigated in Phase 5)
**Phases affected:** 5 (Tool Intelligence)
**Reported:** 2026-08-07

## Symptom

Live Understanding LLM output (probe-verified, real Ollama) for tool-triggering
messages:

| User message | capability (off-enum in bold) | goal | tools | web | entities |
|---|---|---|---|---|---|
| "search the web for the weather in tokyo" | `web_search` | `create` | True | True | `[('Tokyo','location')]` |
| "search google for the latest nvidia gpu prices" | `searching` | `create` | True | True | `[('nvidia gpu','topic')]` |
| "check todays weather in paris" | `information` | `create` | False | True | `[('paris','location')]` |
| "what is the current price of bitcoin" | `information` | `create` | False | True | `[('bitcoin','topic')]` |
| "create a folder for my project" | `file_system` | `open_application` | True | False | `[]` |
| "list the files in my project folder" | `file_system` | `create` | True | False | `[]` |
| "run the ls command in the terminal" | `device` | `open_application` | True | False | `[]` |
| "launch spotify" | `device` | `open_application` | True | False | `[]` |
| "what is 2 plus 2" | `mathematics` | `calculate` | False | False | `[]` |

Same KI-007 pattern as Phase 4: the small model is not on-enum, the `goal`
string value leaks semantic weight (`open_application` appears even for file
operations), and `entities` is frequently empty even when a concrete noun is
present.

## Impact (before mitigation)

A router that trusted `goal` or required entities would either misfire
(`goal=create` for a web search → wrong tool) or never fire (`create a
folder` → no tool at all). Both are broken Tool Intelligence.

## Mitigation (Phase 5 design)

- **Capability-first routing.** The router normalizes observed variants through
  `_CAPABILITY_VARIANTS` (`searching|information|web_search|search` → `web`,
  `file_system|file management` → `automation`, `device_control` → `device`,
  `terminal|system_control` → `system`) and selects a tool on capability alone.
  `goal` is not a routing input.
- **Entity presence gates risky tools.** app_launcher and terminal require a
  non-empty entity. With `entities=[]` the request builder returns `None` and
  no tool fires — the message degrades to a normal text answer. A tool never
  receives garbage input.
- **Permission gate is the safety net.** Only `SAFE` actions run by default;
  write/delete/terminal/app-launch are denied unless granted (env
  `FRIDAY_TOOL_PERMS` or `permission_gate.grant`).
- **Reliable triggers.** `required_systems.tools=True` is reliable, and
  `web=True` fires web_search (checked as an OR with `tools`).

## Residual risk

- "create a folder for my project" fires file_manager with a **list** action
  (safe, capability-gated), not a create — the model produced no entity so a
  write could not be structured. A user must phrase the request so the entity
  is extracted (e.g. "create a file called notes.txt") for a write to fire.
- The canonical `capability` enum is not enforced on the Understanding side
  (that is a future "Stable Understanding" task, same as KI-007).
- The Understanding model is nondeterministic about `goal` and entity labels
  ("photos folder" labeled `application`); the router's label + entity-text
  rescues absorb the observed variants, but an unseen mislabel could still
  route to the wrong tool.

## Suggested future fix

Enforce the on-enum capability contract in the Understanding prompt/parse
layer (schema validation with retry), so the router can drop its variant
table and rescue tables. Tracked with KI-007.

## Phase 5 follow-up (2026-08-07)

The residual risks above are largely absorbed by universal deterministic
fixes added in Phase 5:

- `goal` is no longer a hard routing input; capability (+ entity labels/text)
  drives selection, with a `goal=search_web` override that guarantees an
  explicit web search always fires web_search (this fixed weather/topic turns
  that the small model mislabeled as `device`/`open_application`).
- Router rescues now cover the observed label noise: `_FILE_LABELS` +
  `_FOLDER_TEXT_HINT` (entity text `folder|directory|path`) redirect a
  mislabeled `device` turn onto `file_manager` (fixes "show me my photos
  folder" → application label); `_COMMAND_LABELS` → `terminal`;
  `_NON_APP_LABELS` suppresses app_launcher for query/system/location turns;
  `_NON_FILE_GOALS` keeps weather/web turns out of the file rescue.
- Entity-gated risky tools remain: app_launcher/terminal still require a
  non-empty entity, so garbage inputs never fire.
- Verified: `p6_stress_500.py` 255/255 PASS plus p4/p5 regression suites
  green — memory, web, device, and file routing all stable together with the
  contrast-trio understanding prompt.

## Launcher audit follow-up (2026-08-07)

The KI-009 residual risks were the direct targets of the App Launcher audit
(tracked as the Phase 5 BUG 1–8 launch pipeline):

- **Off-enum capability and `goal=open_application` misrouting.** The router
  now pins `goal == "open_application"` to `device` (after the file/folder
  rescue, so automation still wins), turning the LLM's `web`/`general`
  misclassification of "open spotify"/"launch spotify" into a real
  `app_launcher` call. `goal` remains non-routing for selection.
- **Empty-entity device turns** ("open file manager" with no entity) no longer
  go silent: `execution_manager` synthesizes a failure ToolResult
  (`tool_router/dispatch/no_tool_selected`) whenever a capability resolves to
  a registered tool but no request is routable, and the prompt's non-success
  branch forces an honest "could not do it" reply. Pure flag noise stays
  result-free.
- **Universal app resolution.** `app_catalog` (Start Menu, registry,
  WindowsApps aliases, Steam, Epic, builtins) resolves launches
  deterministically; ambiguity returns a candidate list and never guesses.
- **Honest reporting.** Launcher results carry display names, never paths;
  ambiguous results render a clarification request; the stale-context guard
  is now in BASE_HONESTY_RULES so earlier turns' file listings are never
  echoed as current success.

Residual (documented, not root-fixed): the Understanding model still emits
off-enum capability and unreliable entities — the router absorbs every
observed variant, but the durable fix remains schema validation with retry
at the Understanding layer (tracked with KI-007).

## Launch reliability follow-up (2026-08-07)

Live user test exposed two more observed variants that the router now
absorbs, plus the WindowsApps alias activation bug (that one lives in
`app_catalog`/`app_launcher`, not Understanding):

- **`web` capability + `application` entity label = launch, not search.**
  "launch brave browser" came back capability=web, goal=create, entity
  `(brave, application)` and previously fired `web_search`. The router now
  treats a `web`-capability request with an `application`-labeled entity as a
  launch signal unless the goal is explicitly web
  (`search_web`/`retrieve_web`/`find_information`); genuine searches keep
  `topic`/`query` labels and still hit `web_search`.
- **Entity-less `open_application` recovers the app name from the user's own
  words.** "open file explorer" produced `entities=[]`, so nothing was
  routable. For goal `open_application` + device capability, the router now
  extracts the reference from `raw_text` (`_fallback_app_reference`) —
  folder/path-style text is rejected — and the recovered name still passes
  the safe resolver (found / ambiguous / not_found, never a blind launch).
- **Packaged apps must activate by AUMID, not the WindowsApps alias stub.**
  `os.startfile` on `C:\Users\polis\AppData\Local\Microsoft\WindowsApps\
  Spotify.exe` intermittently leaves no UI process. `app_catalog` now attaches
  `Get-StartApps` AUMIDs to WindowsApps entries and `app_launcher` activates
  them via `explorer.exe shell:AppsFolder\<AUMID>` (startfile fallback) —
  universal for every packaged app, live-verified (Spotify.exe UI running).

Verification: `p5_launch_validation.py` extended to 73 checks (AUMID
launch, startfile fallback, brave rescue, web-search-stays-web, entity-less
fallback, folder-text rejection), all green; p6_stress_500 256/256, p5 and
p4 stress suites, response and honesty probes all re-run green.

## Sequential-launch execution/context follow-up (2026-08-07)

Repeated launch turns in one conversation exposed the last structural-drift
failure layer of KI-009: the Understanding model degrades over a long
conversation from "off-enum but present" to **fully dropped signals**
(`use_tools=False` + dropped launch goal + planning hijack or a `web_search`
misroute on "open steam"). This is now absorbed by two deterministic layers
that never depend on the LLM staying on-schema:

- **Deterministic launch-signal gate** (Layer 1): `has_launch_signal`
  (`goal == "open_application"` or an `application`-labeled entity) forces
  `app_launcher`; `execution_manager` synthesizes an honest failure when a
  resolvable capability has no route; `reasoning_engine` includes the launch
  signal in `use_tools`.
- **Raw-text launch recovery** (Layer 2, `tool_router.py`): `_raw_text_launch_ref`
  strips pre-verb fillers, requires a literal leading `open`/`launch`, and
  recovers the app reference from the user's words (folder/path text and
  single letters rejected). `has_launch_signal` checks raw text first, so a
  raw launch wins even over a drifted `cap=web` goal; `route_tool` sets
  `use_web=False`/`goal_search_web=False` on launch. `reasoning_engine`
  suppresses planning on launch turns.
- **Verified**: new 28-turn sequential harness (`p5_seq_launch.py`) 28/28 —
  every launch turn re-executes and the unknown-app turn reports
  `not_found` honestly; `p5_launch_validation` extended to 74/74
  (R 41, G 15, L 11, P 4, H 3); p6_stress_500 255/255, p5_stress_50 42/42,
  p4_stress_50 64/64, response 5/5, honesty PASS.

Residual (root cause unchanged): the durable fix for the Understanding
nondeterminism itself remains schema validation with retry (tracked with
KI-007). The router/harness now absorbs every observed drift variant, but a
future LLM turn that drifts to something the raw gate cannot parse (no
`open`/`launch` token, no launch goal, no entity) still degrades to an
honest no-tool reply.

## Packaged-app discovery follow-up (2026-08-07)

"launch whatsapp" returned `app_launcher -> not_found`: WhatsApp Desktop is
a packaged (Store/MSIX) app that exposes **no WindowsApps alias stub**, so
the stub-only WindowsApps discovery never indexed it (`Get-StartApps` did:
`WhatsApp -> 5319275A.WhatsAppDesktop_cv1g1gvanyjgm!App`). This is a
**catalog coverage gap, not an Understanding issue** — but it looks like one
from the user's side (no permission window, honest "couldn't do it").

Fix (`app_catalog.py` + `app_launcher.py`): a new discovery source reads
the shell's `Get-StartApps` index once per process and adds every packaged
app whose AppID is a real AUMID (contains `!`), skipped when a
higher-priority source already covers the name. Entries activate via
`shell:AppsFolder`; `_launchable` recognizes AUMID targets; the launcher
fallback retries the shell activation for AUMID-only entries (real-file
targets keep the `os.startfile` fallback unchanged). Dedupe priorities
unchanged — existing behavior untouched.

Verified: `resolve("whatsapp")`/`resolve("whats app")` → WhatsApp; all other
R-battery references unchanged; `p5_launch_validation` 74/74 (whatsapp
expectations corrected — they asserted `not_found` under a wrong "not
installed" comment); `p5_seq_launch` 28/28 live; p6 routing checkpoint
255/255; live `launcher.execute("whatsapp")` → success + `WhatsApp.Root`
running.

## Response-layer follow-up (2026-08-08)

With launches now executing reliably, the residual failures moved to the
**response prompt** (`src/ai/prompt_builder.py`), not Understanding/routing:
the launch tool result succeeded (`launched: True`) but FRIDAY's spoken reply
was wrong. Live examples: "launch whats app" fabricated a file listing
("WhatsApp.exe, WhatsApp.apk..."); "launch lenovo vantage" echoed a
permission refusal ("I'm not sure I can launch... without your permission, as
it's a hardware device..."); "launch microsoft store" rambled about Lenovo
devices from earlier turns.

- **Root cause** — a successful launch rendered in TOOL RESULTS as raw scalar
  lines (`launched: True / detail: WhatsApp`), which the small model does not
  read as "the app is now open" and instead answers with an invented listing
  (primed by the generic file/weather listing wording); the success
  instructions contained no launch rule, so nothing overrode the
  `(hardware)` ENTITIES label and the stale permission-refusal exchange in
  RECENT CONVERSATION.
- **Fix** — `_render_tool_payload` now renders a successful launch as
  `Opened application: <detail>`, and `build_prompt` gained a dedicated
  instruction branch for all-success app-launch turns: the apps are already
  open (never permission talk), confirm each in one short sentence naming the
  app exactly as shown, a launch produces no files/folders so nothing may be
  invented, and ENTITIES MENTIONED + RECENT CONVERSATION must be ignored
  (TOOL RESULTS are the only facts). Universal — no app names or keywords;
  other tool paths keep their existing instructions.
- **Verified** — offline repro of the three failing turns (real prompt +
  real LLM): "WhatsApp is open." / "Lenovo Vantage is open." / "Microsoft
  Store is open.", zero file-list/permission/stale hits; `p5_response_probe`
  5/5, `p5_honesty_probe` PASS. Launcher/router/executor untouched.

This closes the observed KI-009 *response* symptoms. The underlying
Understanding nondeterminism (off-enum `capability`, unreliable
`goal`/`entities`) remains the tracked root cause — schema validation with
retry (KI-007) is still the durable fix.

## Filesystem-contents routing follow-up (2026-08-16/17/18)

The KI-009 drift classes reappeared in the filesystem pipeline and were
absorbed by three more deterministic layers. Full detail in
FILESYSTEM_AUDIT_REPORT sections 11-13; KI-015 is the routing-drift fix.

### Fully-dropped entities → empty_path (2026-08-17)

"tell me whats inside the examples" / "chapter one folder" failed with
`parameters={}` `empty_path` even though parent-context propagation was
proven intact. Two root causes in the raw-text recovery layer:

- `_raw_filesystem_reference` dropped any reference with fewer than 2
  surviving tokens (`len(keep) < 2`) — single-word folder names
  ("examples", "exam") died whenever the model emitted `entities=[]`.
- `"one"` was a `_FS_FRAME_WORDS` member, so "chapter one" stripped to
  nothing.

Fix: a single surviving token is now a valid recovery (junk words still
degrade to an honest `not_found` naming the word); `"one"` removed from the
frame words; compound spoken numbers parsed (`_canonical_tokens` +
`_parse_number_run`: "chapter twenty one" → 21, "two hundred five" → 205;
"twenty twenty" stays literal) applied in `_tokens_match`/`_norm_key`;
`_exact_children` + same-parent canonical ambiguity ("chapter one" with
chapter 10/11 present deterministically → chapter 1, never chapter 10).

### Off-enum capability → web canonicalization misroute (2026-08-18, KI-015)

New twist on the KI-009 capability class: the model emitted `search` — a
label that IS in the variant table — but for a filesystem ask. The table
canonically maps `"search" -> "web"`, so "tell me whats inside the exam
folder" resolved to the web capability and fired `web_search` (real
production log evidence), and the response model invented contents. The
fs-query rescue was blocked by `goal not in _NON_FILE_GOALS` and
`tool_cap != "web"`.

Fix: decisive raw-text gate `_fs_decisive()` in `tool_router.py` (inside
phrase + filesystem noun; list/show/read + filesystem noun; or a
session-verified object via new `context_knows()` in `path_resolver.py` —
registry/context chain only, never a global disk search). Decisive turns
are pinned to `file_manager` with web forced off; genuine web questions
("whats inside a black hole", "whats in the news") are never hijacked.
This extends the raw-text rescue family: where the model's struct is
unreliable, the user's own words win.

### Structural drift over long navigation (2026-08-16/17)

Follow-up asks after multi-level navigation ("python revision" → "chapter
1" → "whats inside the examples") hit the wrong folder — the deterministic
first-hit global fuzzy search picked stale leftover folders. Fix: bounded
session discovery registry + context chain + `last_listed_scope`/
`active_folder_context` in `path_resolver.py` (`_hierarchy_lookup` replaces
the broken Section 5b relative resolution; global search is fall-through
only); `file_manager._list`/`_read`/`_locate` register every verified
object.

Verification (all fresh, 2026-08-18): `test_navigation_flow.py` 18/18,
`test_hierarchy_resolution.py` 13/13, `test_universal_fix.py` 6/6, legacy
live scripts PASS; live simulation with the exact failing log flags routes
`['file_manager']`.

Residual (root cause unchanged): the Understanding model still emits
off-enum/unreliable structs — the durable fix remains schema validation
with retry at the Understanding layer (tracked with KI-007).

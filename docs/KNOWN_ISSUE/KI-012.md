# KI-012 — Known-folder resolution falls back to environment variables when `SHGetKnownFolderPath` is unavailable

Date: 2026-08-08

## Symptom

On a non-Windows host (or any platform where `ctypes.windll` /
`SHGetKnownFolderPath` cannot run), user folders that live in a known
shell location (Desktop, Documents, Downloads, Music, Pictures,
Videos) resolve through the process environment variables
(`USERPROFILE\Desktop`, `USERPROFILE\Documents`, ...) instead of the
shell-known-folder location. On Windows this path is normally
identical; it only differs when a folder is **redirected**, the common
case being OneDrive where `C:\Users\<user>\Pictures` does not exist and
the real folder is `C:\Users\<user>\OneDrive\Pictures`.

Because the env-var fallback is only consulted **after** the shell
lookup and only when the shell lookup returned nothing, the impact is
limited to: non-Windows hosts (cosmetic — the code is Windows-first),
or a Windows host where `SHGetKnownFolderPath` genuinely fails
(missing shell folder, permission edge, exotic runtime). In those cases
the resolved path may not be the user's real, redirected folder.

## Root Cause

`src/utils/path_resolver.py:_known_folder()` resolves known folders in
two tiers:

1. Windows shell lookup via `SHGetKnownFolderPath` (ctypes) — returns
   the real, redirection-aware location. Returns `None` on any failure,
   including `ImportError` for `ctypes.windll` on non-Windows.
2. Environment-variable fallback (`USERPROFILE`, `PUBLIC`, `APPDATA`,
   `PROGRAMFILES`, ...) — returns `%USERPROFILE%\Documents` etc.

The second tier is an intentional, generic fallback so the resolver
still works where the shell API does not; it is inherently unable to
follow OneDrive-style redirection because the redirection lives in the
shell's known-folder table, not in the environment.

## Why it is deferred

- On the supported platform (Windows) the shell tier runs first and
  succeeds for every known folder this machine actually redirects
  (Desktop, Documents, Pictures — all OneDrive-redirected). Verified in
  the Phase 5 harness: `desktop`/`documents`/`photos` all resolve to
  the OneDrive location.
- The fallback is strictly better than failing: on non-Windows the
  env-var paths are the correct convention.
- The resolver is deterministic and read-only; a wrong guess is
  impossible — a redirect-miss simply resolves to a non-redirected
  path that may not exist, which then degrades to an honest
  `not_found` (never a fabricated listing).

## Reproduction

Run `resolve_reference("photos")` on a machine where
`C:\Users\<user>\Pictures` does not exist and the Pictures folder is
OneDrive-redirected, but block the shell call (e.g. run under an
environment without `ctypes.windll`, or monkeypatch
`path_resolver._shell_known_folder` to return `None`). The resolver
falls back to `%USERPROFILE%\Pictures` (a non-existent path →
`not_found`), instead of the real OneDrive location.

## Future approach

- Add a pure-Python fallback for the shell-known-folder table (read the
  per-user registry `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders`)
  when `SHGetKnownFolderPath` is unavailable on Windows.
- On non-Windows, keep the env-var convention (documented behaviour).

No code changed beyond the resolver itself; this issue documents the
inherent limitation of the generic env-var tier. The fix belongs in a
future cross-platform port, not the current Windows-first Phase 5 work.

# KI-015 — Folder-content queries routed to web_search; response model hallucinated folder contents

**Status:** Fixed (2026-08-18)
**Phases affected:** 5 (Tool Intelligence / Routing)
**Reported:** 2026-08-17 (real production log, 08:28–08:32)
**Fixed:** 2026-08-18

## Symptom

Real production log (user's live session) showed every folder-content query
answering from `web_search` instead of `file_manager`, with the response
model inventing contents:

| User turn | Log evidence | FRIDAY's answer |
|---|---|---|
| "tell me whats inside the exam folder" | `Need Tools: False`, `Need Web: False`, `web_search -> success` | "The 'exam' folder contains one entry: test.py" — hallucinated (real contents: ch1_function, ch2_string, ch3_array, ch4_structure, exam_notes.txt, test.txt) |
| "tell me whats inside the lab 3 folder" | `web_search` (rate-limit failure) | honest miss |
| "its inside the c lab folder in my c drive please check" | `web_search` (failure) | "exam1 (file), exam2 (file)" — both invented, neither exists |
| "tell me whats inside this c lab folder in c drive" | `web_search` | hallucinated |

Turns naming "python revision"/"chapter 1"/"examples" earlier in the same
log succeeded — routing was nondeterministic, depending on how the small
Understanding model happened to classify each turn.

## Root Cause

The Understanding model classified the folder asks as
`category=search / goal=search_web / capability=search`, and the router's
capability-variant table canonically maps **`"search" -> "web"**
(`_CAPABILITY_VARIANTS` in `src/core/tool_router.py`). The turn then
resolved to the web capability, and:

1. `tool_required()` — the `fs_query` gate requires
   `goal not in _NON_FILE_GOALS`; `"search_web"` IS in `_NON_FILE_GOALS`, so
   `fs_query` was False — yet the turn still entered the tool path because
   capability `"web"` is in `_CAPABILITY_TO_TOOL`.
2. `route()` — the raw-text fs rescue
   (`if fs_query_text and goal not in _NON_FILE_GOALS and tool_cap != "web"`)
   was blocked by BOTH guards, and the web branch fired on `is_web_cap`
   (capability resolved to "web") even with `use_web=False`.
3. `web_search` returned web snippets; the response model had no real
   listing and invented contents (and reused "test.py" from an earlier real
   listing in conversation).

Not a memory/context bug: the discovery registry and context chain persist
in `src` and nothing clears them. The only broken link was router tool
selection — a fabricated `search` classification was allowed to override the
user's unmistakable filesystem phrasing.

## Fix Applied

**Files:** `src/core/tool_router.py`, `src/utils/path_resolver.py`

Decisive raw-text gate `_fs_decisive()` (module-level, same narrow raw-text
philosophy as the launch gate and the locate rescue — the user's own words
are the only signal the small model cannot fabricate):

1. **Inside/contents phrase + filesystem noun** — `_FS_INSIDE_TEXT_RE`
   (what's/what is inside, what's/what is in, it's/its inside, contents of)
   × `_FS_OBJECT_NOUN_RE` (folder, directory, dir, drive, desktop,
   downloads, documents, file): "whats inside the exam folder", "its inside
   the c lab folder in my c drive", "whats in my c drive". A genuine web
   question never has both.
2. **List/show/read + filesystem noun**: "list my downloads", "read the
   first.py file".
3. **Verb/inside phrase + SESSION-VERIFIED object** — new public
   `context_knows()` in `path_resolver.py` (discovery registry + context
   chain ONLY, never a global disk search): "read first.py", "whats inside
   the examples" right after the user was shown them. "whats inside a black
   hole" is never session-verified, so it is never pinned to the filesystem.

When decisive: `route()` pins `tool_cap="automation"` (before the web
pins can claim it) and forces `use_web=False; goal_search_web=False` (the
launch/locate rescue pattern); `tool_required()` enters the tool path even
with a fabricated web classification and no tool flags.

## Architecture Impact

- Router-only + one public resolver helper (`context_knows()`). No changes
  to execution, prompts, response guards, or memory.
- Follows the established raw-text rescue family (launch gate, locate
  rescue, fs-query rescue) — no keywords, no hardcoded folder names,
  universal for every folder now and in the future.
- Related classes: this is the KI-007/KI-009 class — the Understanding
  model emitting a variant (`search`) that the variant table maps to a
  wrong capability. The durable fix remains schema validation with retry at
  the Understanding layer; the decisive raw-text gate is the current
  backstop.

# KI-010 — "open file explorer" sometimes lists the project files instead of launching, and FRIDAY claims it launched

Date: 2026-08-08

## Symptom

Voice message (live user test):

> "open file explorer"

Intermittently FRIDAY **does not launch** File Explorer but responds as if it
did ("File Explorer is open / launched") and then reads out a list of files
**from this project** (the top-level entries of `C:\project friday`). The
user only sees this with File Explorer; other app launches report correctly.

## Root Cause (reproduced deterministically)

The entity "file explorer" collides with the router's folder/path rescue. The
app is a genuine catalog entry (`app_catalog._BUILTINS` → `File Explorer`,
target `explorer.exe`), and the resolver handles it — but the rescue fires
*before* the launch pin and wins by design:

1. The user's words "open file explorer" are a launch signal
   (`has_launch_signal` via the raw-text gate), so the turn enters the tool
   path with `tool_cap = "device"`.
2. The Understanding model labels the entity. Because the name literally
   contains the word "file", the model **sometimes** labels the entity
   `("file explorer", "file")` (or `location`) instead of `application`.
   This is nondeterministic — hence "sometimes".
3. `route_tool` checks the file rescue first
   (`src/core/tool_router.py:341-346`): `tool_cap == "device"` and the entity
   label ∈ `_FILE_LABELS = {location, file, folder, directory, path}` →
   `tool_cap = "automation"` (file_manager). The rescue exists to send true
   folder/path references ("photos folder") to file_manager, not to launch.
4. The `open_application` launch pin
   (`tool_router.py:354`: `goal == "open_application" and tool_cap !=
   "automation"`) is deliberately **blocked** once the rescue has set
   `automation`, so it cannot undo the hijack.
5. file_manager fires `list` with **no path**, which defaults to the workspace
   root `DEFAULT_BASE` (`src/skills/file_manager.py:86-87`) → `C:\project friday`.
6. The response model receives the project's file names as `- name (type)`
   lines under a `list` action. The generic success instructions tell it the
   action "complete" and to judge by the action that ran, but for the small
   model the visible success + the user's request is enough to narrate "File
   Explorer is open" and then read the file names aloud.

Offline confirmation with the real router (`route_tool`):

```
entity label='application'  -> [('app_launcher', 'launch', {'app': 'file explorer'})]
entity label='file'         -> [('file_manager', 'list', {})]
entity label='location'     -> [('file_manager', 'list', {})]
entity label='folder'       -> [('file_manager', 'list', {})]
```

So the mis-launch is **deterministic once the label is `file`/`location`**;
the intermittency is entirely the Understanding model's label choice. The
same hazard applies to any app whose display name contains a `_FILE_LABELS`
word or whose entity gets a folder/path-style label — "file explorer" is just
the common case.

## Why it is deferred

- User-classified as a minor issue; no crash, no wrong file operation (the
  list is read-only and sandboxed), and the only real harm is a wrong spoken
  claim plus an unexpected file listing.
- The conflict is architectural: one deterministic rescue that must send real
  folder references to file_manager vs. a real app whose name triggers the
  same label. Resolving it needs a priority rule ("a launch signal with a
  resolvable app name wins over the file rescue unless the reference is an
  actual folder/path") — a routing change the user asked not to make now.
- The spoken "it's open" half is a soft-instruction gap: the small model does
  not consistently apply the existing "judge completion by the action that
  ran, not the user's wording" rule.

## Reproduction

1. Start a fresh session.
2. Say "open file explorer".
3. Repeat a few times — when the Understanding model labels the entity
   `file`/`location` instead of `application`, no File Explorer window opens
   and FRIDAY says it opened it and lists `C:\project friday`'s files.

## Future approach

- Router: before applying the `_FILE_LABELS` rescue, resolve the entity text
  as an app; if the launch signal is raw ("open/launch <app>") and the
  reference resolves to a real app (found), keep it on `app_launcher`. Reserve
  the rescue for entity text that is actually a folder/path reference (the
  `_FOLDER_TEXT_HINT` / `folder|directory` words), not bare `file`/`location`
  labels on a launch command.
- Response: strengthen the "action label is the truth" rule so a `list`
  result is never narrated as a launched application. The durable fix is the
  KI-007/KI-009 schema-validated Understanding layer, plus possibly a larger
  response model for tool turns.
